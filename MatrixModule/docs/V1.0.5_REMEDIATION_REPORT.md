## 2. Finding 1: Exact Installer Permission Verification (`customize.sh`)

### 2.1 Problem Analysis
In v1.0.4, `verify_installed_permissions()` in `customize.sh` tested permissions using basic `-x` and `-r` tests:
- Executable files checked `[ ! -x "$f" ]`
- Non-executable files checked `[ -x "$f" ]`

This allowed overly permissive permissions to slip through undetected:
- A script set to `0777` (world-writable) passed because it was executable (`-x`).
- `module.prop` set to `0600` passed because it was non-executable (`! -x`), even though non-root processes could not read module metadata.
- Root directory set to `0700` passed even though standard manager sandboxes require `0755` traversability.
- Persistent data directory set to `0755` passed even though sensitive configs and logs require strict `0700` isolation.

### 2.2 Technical Solution
In `customize.sh`, portable mode and ownership helpers were implemented:
```sh
get_octal_mode() {
    _f="$1"
    # Try GNU / toybox / BusyBox stat
    _m=$(stat -c "%a" "$_f" 2>/dev/null)
    if [ -n "$_m" ]; then
        echo "$_m" | sed 's/.*\(...\)$/\1/'
        return 0
    fi
    # POSIX ls -ld fallback (parses 9-bit mode string)
    _ls=$(ls -ld "$_f" 2>/dev/null | awk '{print $1}')
    if [ -n "$_ls" ]; then
        # rwxr-xr-x -> 755
        ...
    fi
}
```

Enhanced `apply_perm` and `apply_perm_recursive`:
- Checks exact mode match post-application, failing fast even if `set_perm` returned exit code 0.
- Checks root ownership (`root:root` / `0:0`) when installer executes under root (`id -u == 0`).
- Non-fatal warning handling for filesystems lacking SELinux label support.

Rewrote `verify_installed_permissions()` with strict octal assertions:
- **Scripts:** Exact mode `0755` (`service.sh`, `post-fs-data.sh`, `action.sh`, `uninstall.sh`, and `core/*.sh`).
- **Metadata & Assets:** Exact mode `0644` (`module.prop`, `webroot/*.html`, `webroot/*.css`, `webroot/*.js`).
- **Module Directories:** Exact mode `0755` (`$MODPATH`, `$MODPATH/core`, `$MODPATH/webroot`).
- **Persistent Data & Logs:** Exact mode `0700` (`$DATA_DIR`, `$LOG_DIR`).
- **Ownership:** `root:root` / `0:0` verified for all files and directories when running as root (`id -u == 0`).

## 3. Finding 2: Honest Unknown Boot-State Reporting (`core/matrix_health.sh`)

### 3.1 Problem Analysis
In v1.0.4, state precedence permitted edge cases where an uninitialized boot stage (e.g. before `post-fs-data.sh` executed) or unavailable environment probes could be masked or improperly classified as healthy or generic warnings.

### 3.2 Technical Solution
In `core/matrix_health.sh`, `matrix_health_determine_status()` was refactored to establish a strict four-tier precedence hierarchy:
$$\text{ERROR} > \text{UNKNOWN} > \text{WARNING} > \text{HEALTHY}$$

```sh
matrix_health_determine_status() {
    # Tier 1: Critical System Errors (ERROR)
    # - Active recovery mode (post-fs-data-recovery)
    # - Boot explicitly aborted or failed
    # - Persistent boot_failure_count > 0
    # - Unsupported CPU architecture

    # Tier 2: Unresolved System State / Probes (UNKNOWN)
    # - Boot stage is unknown, uninitialized, or empty
    # - Root Manager unresolvable ("Unknown")
    # - SELinux policy unresolvable ("Unknown")
    # - Android SDK level unresolvable ("Unknown")
    # - Architecture unresolvable ("Unknown")

    # Tier 3: Subsystem Warnings & Incomplete Transitions (WARNING)
    # - Boot stage is "post-fs-data" (early boot incomplete)
    # - Boot stage is "timeout" (sys.boot_completed exceeded timeout)
    # - KernelSU driver/manager version mismatch (ksu_version_match == 0)
    # - Active conflicting modules detected

    # Tier 4: All Checks Passed (HEALTHY)
    # - boot_stage == "completed"
    # - All environmental probes fully resolved and supported
    # - Zero mismatches, zero conflicts, zero failures
}
```

In addition, fallback logger definitions (`log_info() { :; }`, etc.) were added to `core/matrix_health.sh` to prevent `command not found` errors when invoked in isolated subshells without `core/matrix_log.sh`.

## 4. Finding 3: Boot Completion Timeout & Lifecycle Error Wiring

### 4.1 Problem Analysis
In v1.0.4, `service.sh` waited up to 120 seconds for `sys.boot_completed=1`. However, if the loop timed out without `sys.boot_completed=1`, execution continued past the loop and called `matrix_health_mark_boot_complete "$_boot_duration"`, falsely marking a timed-out boot as successfully completed. Furthermore, boot failure and abort events were not tracked in persistent state.

### 4.2 Technical Solution
1. **Timeout Handling in [`service.sh`](file:///home/neuro/Projects/MatrixModule/MatrixModule/service.sh):**
   - The wait loop checks `getprop sys.boot_completed`.
   - If `_boot_completed == "1"`, it records boot duration and calls `matrix_health_mark_boot_complete "$_boot_duration"`.
   - If the timeout expires without `sys.boot_completed=1`, it calls:
     ```sh
     matrix_health_mark_boot_timeout "$_timeout_sec" "sys.boot_completed not 1 after ${_timeout_sec}s"
     ```
   - It logs a warning and proceeds to run the watchdog without falsely asserting completion.
2. **Lifecycle Error Wiring in [`post-fs-data.sh`](file:///home/neuro/Projects/MatrixModule/MatrixModule/post-fs-data.sh):**
   - When recovery mode is detected (`/data/adb/modules/.disable_magisk` or KernelSU safe mode flag), it invokes:
     ```sh
     matrix_health_mark_boot_aborted "Recovery mode detected"
     ```
3. **Failure Telemetry in [`core/matrix_health.sh`](file:///home/neuro/Projects/MatrixModule/MatrixModule/core/matrix_health.sh):**
   - Implemented `matrix_health_mark_boot_failed()`: increments persistent `boot_failure_count` in `$MATRIX_STATE_FILE`.
   - Implemented `matrix_health_mark_boot_timeout()`: sets `boot_stage=timeout` and saves `boot_timeout_reason`.
   - Health JSON generator embeds `"boot_failure_count": <count>` into the output.

### 4.3 Verification & Test Proof
Automated tests in [`tests/test_boot_mock.sh`](file:///home/neuro/Projects/MatrixModule/MatrixModule/tests/test_boot_mock.sh):
- **Test 3a:** Normal boot completion sets `boot_stage=completed` and status `HEALTHY` -> **PASS**
- **Test 3b:** Boot timeout sets `boot_stage=timeout` and status `WARNING` -> **PASS**
- **Test 3c:** Boot failure increments `boot_failure_count` from 1 to 2 and status evaluates to `ERROR` -> **PASS**
